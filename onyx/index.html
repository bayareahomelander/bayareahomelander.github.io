Onyx

Grammar-constrained LLM inference engine

Onyx makes an 8B model generate up to 2.4× faster while producing exactly the same output, token for token. A small draft model guesses ahead; the large target model checks every guess in one pass and keeps only what it agrees with. A Rust grammar engine forces every token to fit a regex or JSON Schema, so structured output is valid by construction.

4 Grammar playground

Constrained generation, one token at a time. A token is legal only if every character in it can be consumed from the current grammar state, the way Onyx scans each token's raw bytes.

5 How it got there

  1. 5.1 The draft runs as hand-written CUDA graphs.

    Reimplementing the draft's decoder step over a static KV cache cut it from 7.5–9.8 to 4.1–4.4 ms per token, and raised the overall speedup from 1.17× to 1.49× in one week.

  2. 5.2 Output stays bitwise-identical.

    Scoring several positions at once can round differently in FP16. When the top two scores are within rounding of each other, Onyx replays the history one token at a time from a clean checkpoint, using CUDA graphs in 8-token blocks.

  3. 5.3 Grammar masks live on the GPU.

    A Rust engine (regex DFAs and a stack-based JSON Schema parser, exposed through PyO3) works out which tokens are legal in each state. Caching those scans by grammar state lifted long constrained outputs from 0.49–0.99× to as high as 2.0×.

  4. 5.4 Speculation costs almost nothing up front.

    The draft prefills the prompt only after the target has picked the first token, which cut speculation's added time to first token from 637 ms to 0.3 ms.
