Flint

GPT-2 from scratch on hand-written CUDA kernels.

Flint is a from-scratch GPT-2 training and inference stack in C++ and CUDA. The goal is to train GPT-2 124M on one RTX 2080 Ti using only hand-written CUDA kernels, with no cuBLAS, cuDNN or PyTorch at runtime, then serve that model and OpenAI’s GPT-2 checkpoints through Flint’s own inference kernels.

Training GPT-2 without PyTorch has been done before; llm.c, for one, calls cuBLAS for its matrix multiplies. Flint uses no NVIDIA math libraries at all. Its GEMMs are hand-written tensor-core kernels, it is built to train in FP16 with loss scaling on Turing, and its speed is reported against cuBLAS and against the GPU’s measured peak, not in isolation.

C++17, CUDARTX 2080 Ti (Turing) and RTX 4050 Laptop (Ada)Repository on GitHub, MIT license

Progress

  1. M0Setup

    Done, October 2026

    CMake builds for both GPUs on Linux and Windows, a C API, a pytest bridge to PyTorch, compute-sanitizer runs, and a benchmark harness with a strict timing protocol.

  2. M1Tensor-core GEMM

    Done, released as v0.1.0 in October 2026

    FP16 GEMMs with FP32 accumulation in the three layouts a linear layer’s training step needs, with fused bias, bias + GELU, GELU-backward and bias + residual epilogues. Results below, and the full write-up in the repository.

  3. M2One training step matching PyTorch

    In progress, to be released as v0.2.0

    • Every kernel of GPT-2’s forward and backward pass is written: LayerNorm, token and position embeddings, attention’s batched GEMMs, causal softmax, a fused softmax and cross-entropy output layer, and the bias gradient, each with its backward pass.
    • The full forward and backward pass is assembled in C++, with one up-front memory allocation.
    • It is verified against PyTorch on GPT-2 124M, both at initialization and with OpenAI’s weights on real FineWeb-Edu text. With OpenAI’s weights, Flint’s forward pass matches Hugging Face transformers, and all 148 parameter gradients pass the correctness gate, the closest at 2.02 of an allowed 3 on the 2080 Ti.

    Still to come: the gradient norm with overflow detection, AdamW with loss scaling and clipping, safetensors checkpoints, the data loader, a training program with bit-identical resume, a 500-step loss comparison against PyTorch, and Flint’s first end-to-end tokens per second. No model has been trained by Flint yet; the training loop lands at the end of M2.

  4. M3Flash attention on Turing

    Planned

    Forward and backward. M2’s attention is deliberately simple, GEMMs plus a softmax kernel, so M3 has a known-good path to replace.

  5. M4The long run

    Planned

    GPT-2 124M trained on 10B FineWeb-Edu tokens, already tokenized, and evaluated on HellaSwag against OpenAI’s checkpoint. For reference, measured in advance: PyTorch with torch.compile trains the same model on the same GPU at 44.3k tokens/s, about 2.6 days per 10B tokens.

  6. M5Inference

    Planned

    KV cache, decode attention, int8 weights, and OpenAI’s checkpoints up to 1.5B parameters.

Inside one GEMM

Almost all of a transformer’s arithmetic is matrix multiplication. A fast GEMM is mostly about moving data: keeping the tensor cores fed without waiting on memory. Step through how a tiled tensor-core GEMM does it.

A sketch: the 8 × 8 grids stand in for matrices with thousands of rows, and the tile sizes are not Flint’s.

Same numbers, same bits

The weight-gradient GEMM sums over all 8,192 tokens, so Flint splits that long dimension across thread blocks and then adds their partial results. Floating-point addition isn’t associative: the same numbers added in a different order can give a different answer. If partials are added in whatever order the blocks happen to finish, two runs can disagree. Flint adds them in a fixed order, so every run is bit-identical.

Try it. These are eight real FP32 partial sums, added with real FP32 arithmetic in your browser.

    These partials nearly cancel, which makes the effect large enough to see. In a real GEMM the differences usually sit in the last bits, but any difference breaks bit-for-bit reproducibility.

    The fused GELU kernels beat cuBLASLt mostly because cuBLASLt runs those epilogues as a separate kernel on Turing. The 2080 Ti’s 53.8 TFLOPS rated peak assumes its 1,545 MHz reference boost; under these loads it runs at 1,630–1,810 MHz, power-capped.

    Where the remaining gap comes from

    Profiling with Nsight Compute, Nsight Systems, a time-versus-K sweep and static SASS analysis puts the gap to cuBLAS down to four things: the main loop, which runs at 93–96% of cuBLAS’s per-cycle rate; a fixed cost of 22–42 µs per call; power-capped clocks; and cuBLAS’s choice of kernel.

    Limitations

    • The GEMMs accumulate in FP32 on the tensor cores, which truncate, so K is capped at 65,536.
    • Results are bit-identical from run to run on one GPU, not across GPUs.
    • The 2080 Ti’s clocks are logged, not locked, and its GEMMs run power-capped.

    Source: Flint README; every number links to a raw JSON log in M1.md, which also gives ranges, clocks and power.

    How it’s checked

    A correctness gate tied to PyTorch’s own error

    Flint’s error against an FP32 PyTorch reference has to stay within a fixed multiple of the error of PyTorch’s own mixed-precision training (autocast FP16 with GradScaler): 2× for forward outputs and 3× for gradients, by both relative L2 and max-abs error, with floors at FP16 or FP32 rounding.

    About 5,300 tests, on both GPUs, on every commit

    Every commit is built and tested on both GPUs before it lands, including runs of all four compute-sanitizer tools: memory, race, synchronization and initialization checks. Deliberate canary bugs prove the tools are actually reporting.

    Bit-identical runs, diffed machine code

    Results are bit-identical from run to run on one GPU. Changes are checked by diffing the compiled machine code (SASS) of every kernel between builds.

    Benchmarks that can’t flatter themselves

    Benchmarks interleave Flint and the baseline, discard rounds disturbed by other GPU activity, and report the percentage of both the rated and the clock-adjusted peak. A tensor-core microbenchmark reaches about 99% of the clock-adjusted peak.

    Notes from the work

    One failing memory cell

    An intermittent test failure at full model size turned out not to be Flint’s fault. A memory test with no Flint code in it traced it to a single failing memory cell on the 2080 Ti; consumer cards have no ECC. The tests now retry once at a different memory placement, and pass only if the difference between the attempts matches that one cell’s signature. How to protect the multi-day M4 run is still to be decided.

    Reading the clock on the GPU itself

    On the laptop, NVIDIA’s management library updates its GPU clock reading only about every 500 ms, so short benchmark rounds read a stale clock. The tensor-core benchmark now measures the clock on the GPU: a tiny probe kernel reads one SM’s cycle counter and the global timer around each sample, leaving the measured kernel’s machine code unchanged.
